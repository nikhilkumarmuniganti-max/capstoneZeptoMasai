# Module 1 — Data Pipeline (`/data_pipeline`)

Scrapes live catalogue data from [books.toscrape.com](https://books.toscrape.com/),
cleans it into proper types, converts prices from GBP to INR at a fixed rate, loads it into a
normalized SQLite database, and queries it with both SQL and pandas.

```
scrape.py  ──>  clean.py  ──>  database.py  ──>  queries.py
 raw CSV        typed CSV       SQLite (PK/FK)    6 SQL queries + pd.read_sql + pd.merge
```

## How to run

From the repository root, inside the virtual environment described in the [root README](../README.md):

```bash
pip install -r data_pipeline/requirements.txt   # requests, beautifulsoup4, truststore, pandas
cd data_pipeline
python run_pipeline.py                 # scrape live -> clean -> load -> query
python run_pipeline.py --skip-scrape   # same, but reuse the committed data/raw_books.csv (no network)
```

Each step can also run alone: `python scrape.py`, `python clean.py`, `python database.py`,
`python queries.py`. The runner exits with a non-zero code if the SQL JOIN and the pandas merge
ever disagree.

## Scope of the scrape

Three categories, **all** of their listing pages: **Mystery (32), Fantasy (48), Historical Fiction (26) = 106 books**
(the brief requires at least 60 books across at least 3 categories). Fields captured per book: `title`,
`price` (e.g. `£47.82`), `star_rating` (e.g. `Four`), `availability` (e.g. `In stock`) and `category`.

- The full title comes from the link's `title` attribute; the visible link text is cut short on the site.
- The page is parsed from raw bytes so that BeautifulSoup honours the page's UTF-8 declaration.
  (`response.text` guesses ISO-8859-1 and turns `£` into `Â£`.)
- Every request calls `raise_for_status()` and has a 20-second timeout, and there is a 0.3 s pause between
  pages to be polite to the practice site.

## Cleaning decisions

| Column | Rule |
|---|---|
| `price_gbp` (float) | Take the numeric part of the price text: `£47.82` → `47.82`. |
| `rating` (int 1–5) | Map the words `One`…`Five` to the integers 1–5 (case-insensitive). |
| `in_stock` (bool) | Text starting with `In stock` → `True`, text starting with `Out of stock` → `False`. |
| `price_inr` (float) | `price_gbp × 105.50`, rounded to 2 decimals. |

**Currency rate: `1 GBP = 105.50 INR`.** This is the project's fixed baseline constant (`GBP_TO_INR` in
`clean.py`). It is not a live or historical market rate, so no API call or date lookup is involved.

**Rows that fail to parse — what I chose and why.** The pipeline never crashes on messy rows:

- **Numeric fields (`price_gbp`, `rating`) → median imputation.** A single unreadable value should not
  cost us an otherwise valid book record. I impute with the median of the rows that *did* parse, because
  the median isn't pulled by extreme prices. For `rating` the median is rounded to stay an integer from 1 to 5.
- **`in_stock` → drop the row.** A yes/no field has no meaningful median. Guessing whether a book is in
  stock would publish wrong availability data, which is exactly what this benchmark exists to report.
- **Missing `title` or `category` → drop the row.** These identify the book and supply its category foreign
  key, so they can't be imputed.

On the live data all 106 rows parsed cleanly, so nothing was imputed or dropped. To prove the rules work,
`clean.messy_rows_demo()` (run as part of `run_pipeline.py`) feeds in five deliberately broken rows. It
imputes one bad price (`N/A`) and one bad rating (`Seven`), and drops one row with unknown availability
(`Ask in store`) and one with no title, all without an error.

## Database schema

```sql
CREATE TABLE categories (
    category_id   INTEGER PRIMARY KEY,
    category_name TEXT NOT NULL UNIQUE
);

CREATE TABLE books (
    book_id     INTEGER PRIMARY KEY,
    title       TEXT    NOT NULL,
    price_gbp   REAL    NOT NULL,
    price_inr   REAL    NOT NULL,
    rating      INTEGER NOT NULL CHECK (rating BETWEEN 1 AND 5),
    in_stock    INTEGER NOT NULL CHECK (in_stock IN (0, 1)),
    category_id INTEGER NOT NULL REFERENCES categories(category_id)
);
```

- **Normalized design.** Each category name is stored once; books reference it through the integer
  `category_id` foreign key.
- **Enforced foreign key.** `PRAGMA foreign_keys = ON` is set on every connection, so inserting a book with
  an unknown `category_id` fails with `FOREIGN KEY constraint failed`.
- **Booleans.** SQLite has no boolean type, so `in_stock` is stored as 0/1 with a `CHECK` constraint.
- **Rebuilt every run.** The database file is deleted and rebuilt on each run, so the pipeline always
  produces the same result and a stale database can't linger.

## Queries

All query text and output are in [`outputs/query_results.md`](outputs/query_results.md).

| # | Clause(s) demonstrated | Question |
|---|---|---|
| Q1 | `SELECT` / `WHERE` | Five-star books in stock for under £20 (4 rows) |
| Q2 | `ORDER BY` + `LIMIT` | The 10 most expensive books |
| Q3 | `DISTINCT` | Distinct star ratings in the catalogue (5 → 1) |
| Q4 | `BETWEEN` + `IN` | 4- or 5-star books priced between INR 2,000 and 3,000 (11 rows) |
| Q5 | `JOIN` (+ `ROW_NUMBER()` window) | The 5 highest-rated books per category (15 rows) |
| Q6 | `JOIN` + `GROUP BY` | Book count, average price (GBP and INR) and average rating per category |

**SQL vs. pandas.** Q5 and Q6 are read back into DataFrames with `pd.read_sql`. Q5 is then rebuilt **without
SQL** by `pandas_join()`, which does the following:

1. `pd.merge` the in-memory `books_df` and `categories_df` on `category_id`.
2. Sort with the same keys as the SQL window function: rating DESC, price_gbp DESC, title ASC.
3. Number the rows within each category with `groupby().cumcount()` and keep the top 5.

`pd.testing.assert_frame_equal` confirms the two results are identical: same rows, same values, same order.
The side-by-side table is in Part 3 of `outputs/query_results.md`.

The tie-breakers matter. Every category has at least five 5-star books, so ordering by rating alone would
not produce a stable top 5.

## Environment notes (Windows)

- **HTTPS through antivirus.** On the development machine, Avast Web Shield intercepts HTTPS and re-signs
  certificates with its own root, which Python's default `certifi` bundle does not trust. `scrape.py`
  therefore uses [`truststore`](https://pypi.org/project/truststore/) to verify certificates against the
  operating system's store. Certificate verification stays **on**. On machines without such software,
  this changes nothing.
